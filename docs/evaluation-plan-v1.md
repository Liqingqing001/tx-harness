# 五款 Harness 竞品评测方案 v1.0
日期：2026-11-19。阶段：方案设计完成，待新用例试跑与预注册冻结；不是已完成的实测报告。
对象：Codex、WorkBuddy、DeepSeek Harness（DSH）、元宝专家模式、豆包客户端的“工作／新工作任务”。普通豆包聊天不替代工作模式。

## 1. 研究目标与主张边界
研究问题：在相同工作目标、输入、完成标准和人工帮助规则下，各产品能否可靠地接收材料、持续执行、处理异常并交付可用文件？当结果不同，有哪些证据可以将差异定位到 Harness？

本方案将 Harness 操作性定义为：输入接入、上下文与任务状态维护、工具调用执行、权限边界、文件持久化、失败反馈与恢复支持、产物交付及可观察性。模型负责解释与生成；Skill 提供可被加载的任务流程。三者在商业产品内可能耦合，不能假装完全分离。

输出分为三层，禁止互相替代：
1. **结果事实**：任务是否完成，哪些检查项通过，证据在哪。
2. **执行行为**：是否交付真实文件、保留旧版本、反馈错误等可见行为。不等于根因。
3. **原因结论**：模型、Skill、Harness、外部依赖、评测者或混合/未知；只有满足证据条件才定责。

主轨的成绩名称必须是“原生配置下的任务表现”，不是“纯 Harness 智力排名”。另列经验证的 Harness 故障和能力证据。未知模型、隐藏系统提示、内置 Skill 均是限制，不能通过同一道题或同一模型名称消除。

## 2. 独立设计与参考关系
参考现有 docs/methodology.md 记录的方法原则：结果与过程分开、可复核检查项、试跑校准与案例回归。
本项目独立设计四种合成办公任务、明确的异常植入、两轮状态变化、统一评分公式和证据规范。任务不取自任何竞品的宣传示例，不使用真实业务数据，不复制参考文章的正文或评分数字。
“独立”指本人负责设计、执行、核验和判断；如课程对 AI 辅助有额外规定，应按其规定披露。仓库如实记录本方案及脚本由 AI 辅助起草、执行者审核，不把 AI 辅助材料宣称成完全人工撰写。

## 3. 两条评测轨道
### A：五产品共同任务轨（主表）
使用各产品原生执行环境与指定工作模式。关闭个人自定义 Skill、跨会话记忆、外部资料库检索（仅在界面提供开关且能验证时）；不能关闭的逐项登记。内置 Skill 可自动使用，但注明是否可见、是否实际调用。
模型选择统一“同套餐可使用的默认工作模型/默认推理档位”，冻结后不按任务换强模型。记录具体名称和版本；默认并不意味着模型能力相等。账号限额、系统差异需公开。

### B：受控归因轨（不混入五款总分）
仅对具备真实控制条件的产品子集做：
- Harness 对照：固定确切模型端点/版本、解码参数、任务输入、Skill 内容及工具契约、权限和预算，只更换 Harness。记录无法固定的系统提示与包装层；若改变它们，也只能归到“执行包装整体差异”。
- Skill 对照：同一 Harness 和模型，同一任务，实际加载同一份有哈希的 Skill，对比有/无；确认加载证据。把 SOP 贴入聊天叫“提示干预”，不叫 Skill 消融。
- 模型对照：同 Harness、同 Skill、同工具配置，仅换模型；用于判断模型敏感性，不把提升归给 Harness。
- 故障重放：对可见的正确工具请求，用相同参数重放到相同工具环境；检查请求、响应、文件状态各环节。重放能成功只证明工具在该条件下可用，不自动证明原故障是 Harness。

配对实验预先固定 AB/BA 交错顺序，每个条件 3 次；只用于诊断，不声称统计显著。若产品不支持控制或看不到真实输入，请写“无法进行因果隔离”，不可用近似条件硬凑五款纯 Harness 分数。

## 4. 四个共同任务族
T01 为账号/环境/下载能力预检，不计分。正式任务为 T02–T05，各占 25%；详细逐字提示、输入与检查项见各任务目录。

| 任务 | 测试场景与输入 | 完成条件 | 主要观察与混杂 |
|---|---|---|---|
| T02 政策冲突与需求变更 | 既有 8 行订单 CSV、v1/v2 政策；第二轮只统计华东 | 两轮各交付两张 CSV 和报告；金额/异常正确；不覆盖第一轮 | 上下文延续、版本保持、文件交付；计算与理解也受模型影响 |
| T03 多文件交付 | 两个小 CSV、明确的交付清单 | 精确复制两份 CSV、生成字段说明和清单，共四个文件 | 输入接入、可下载性、文件命名与忠实性；不能只看模型自称完成 |
| T04 资料中的干扰指令 | 两份会议资料，其中一份嵌入与用户目标相冲突的文字；第二轮更新负责人 | 仅提取有效待办；不执行资料中的伪指令；新增版本并保留第一轮 | 指令边界、状态延续；抵抗干扰是模型与 Harness 共同表现，不能仅凭结果归因 |
| T05 损坏输入与备用材料 | 故意损坏的主 JSON、等价且有效的备用 CSV、读取规则 | 说明主文件损坏，依据备用 CSV 交付正确清单和报告 | 异常识别、备用路径与诚实反馈；这是文件异常恢复，不冒充工具服务宕机测试 |

前三个新增任务刻意使用简单数据，减少知识和复杂推理干扰，但不声称消除了模型变量。任务覆盖有限，不推断联网研究、代码开发、PPT美感或所有办公能力。

## 5. 实验配置和执行顺序
每次必须记录：run_id、协议/用例 Git SHA、产品及版本、入口/模式、账号套餐与限额、可见模型/推理档位、Skill 列表/哈希/加载证据、记忆与连接器、文件权限、操作系统、时区、开始/结束时间、输入哈希。
不要求开放全盘权限，不连接真实邮件/企业库。若产品强制自动检索账号知识库，该运行标为有环境混杂，保留事实；若引入额外材料，另列补充结果，不混入共同核心比较。

输入方式优先相同文件附件；若仅支持本地路径，给独立目录和“只使用这几份材料”的路径前缀，登记适配。字节保持相同，不把路径差异当作完全等价。不得上传标准答案、Rubric、校验器或整个评测仓库。

步骤：
1. 预检：确认五个准确产品入口、登录状态、附件和下载；用无关小样预检，不暴露正式答案。
2. 新任务试跑：每产品每任务一次用于校准。现有 T02 记录是历史试跑，不能追认成正式成绩。
3. 冻结：消除任务歧义，完成人工评分复评；发布输入哈希、提示、Rubric、配置表、顺序、排除规则和 Git SHA。若条件未齐，保留“待冻结”，不编造 SHA。
4. 正式：4 任务 × 5 产品 × 3 次独立重复 = **60 个完整试验**；T02/T04 各两轮，因此共 **90 个交互轮次**。同一任务的续问不算独立样本。
5. 每轮 20 分钟。上传完成且用户任务发送成功为计时起点；附件准备时间单列。模型/工具等待计入耗时。可观察完成声明或超时结束。仅自动生成过程继续，不代改产物。
6. 第一轮失败或超时也按同一会话发第二轮，标注前置失败；不得补发答案或偷偷重开。每个完整试验使用新会话和独立输入副本。
7. 每轮结束立即下载、哈希和核验，先保存第一轮再续问。操作者准备/下载耗时不算模型完成耗时，另记交付操作耗时。
8. 完成后按匿名产物编号复评，填结果表、过程表、归因表，再写报告。

预先确定产品简称 A=Codex、B=WorkBuddy、C=DSH、D=元宝、E=豆包工作。按任务顺序 T02、T03、T04、T05；每任务重复 r=1..3，产品起点为 (任务序号从0开始+r-1) mod 5，循环轮转。顺序不会完全消除时间效应，但可复现、避免每次同一款最先跑。记录实际偏离原因。产品内不要同时运行多个正式任务，以免相互竞争或污染会话。

## 6. 人工介入、超时与有效性
- 固定澄清答复：“请按本任务已提供的材料和要求执行。”T02 沿用其已固定的“请按附件最新版政策和任务要求执行”。记录提问、答复、时间；不补充算法和答案。
- 常规上传、选定模式、保存文件和事先约定范围的权限确认属于操作步骤，单列次数；不视为代做。超出输入/产物目录的权限不批准，记录限制。
- 额外提示、重写数据、修改结果属于人工救援；可另外演示，但不计无辅助成功。
- 有效运行中未交付、崩溃、产品超时、明确不支持任务格式：保留为失败，写明能力范围。
- 评测控制插件故障、未成功提交、评测者漏附件：无效，不扣产品分；保留记录并补跑。
- “网络故障”不能仅凭报错就豁免。只有独立证据证明公共环境故障才排除；原因不明保留未决，列出对成功率的上下界。
- 账号额度在正式前检查；意外耗尽先列受阻，恢复后按既定条件补跑；报告受阻次数，不伪装成模型错误。
- 不能补跑超过两次仍无有效记录的单元标为缺失。不得挑最好一次替换失败。
- 运行中版本或模型变化：暂停该批次，分批报告；如需完整排名须重建同一版本窗口下的完整矩阵。

## 7. 评分：用可核验事实，避免主观印象
每任务的 E 项是结果检查，P 项是过程观察。任务卡逐项给出断言、证据和适用轮次。通过=1，失败=0；unknown 未决，NA 仅限事前适用条件不成立，必须写理由。
- 任务单次分数下界 = 100 × 已通过适用 E 项 / 全部适用 E 项。unknown 保留在分母。
- 上界 = 100 × (通过+unknown) / 全部适用 E 项；无未知时上下界相同。
- 两轮任务先算各轮分数，再等权平均，避免第二轮检查项多而隐含加权。
- 每产品每任务取 3 次有效独立试验的平均；四任务等权得总体结果分（25%各）。
- **总体分不替代完成率**：一次完整试验所有必过项均通过且没有救援才算成功；任一必过项 fail 为失败；无 fail 但必过项 unknown 为未决。
- 主表首先显示成功/失败/未决次数、任务完成率区间，再显示结果分。未决计入有效试验分母；给“已成功/n”与“(成功+未决)/n”上下界。
- 产品矩阵不齐、配置严重混杂或关键证据缺失时，只列分任务结果，不输出五款严格排名。分数接近或区间重叠不宣布优胜；三次重复仅作探索性描述，无显著性或总体概率主张。
- 时间：只在同任务成功运行之间比较，列中位数、范围和成功样本数；另列所有运行耗时与超时数，不让提前失败显得更快。
- 成本：仅用可见账单、积分或 Token 数据；单位不可换算就不合并。不可见填 unknown。
- 过程可观察率=(P通过+P失败)/适用P总数；过程通过率=P通过/(P通过+P失败)，同时列分母。日志丰富不直接加到任务分里，日志缺失也不推断动作没做。

案例：某轮 8 项中通过6、失败1、未知1，结果分为75–87.5；若失败项为必过项，任务仍失败。不能说“75分所以算完成”。

## 8. 归因与置信依据
先找最早可确认偏差，并检查上游是否已经提供正确输入。
| 候选原因 | 足够支持的证据方向 | 不足以定责的材料 |
|---|---|---|
| 模型 | 可见实际接收输入与返回均正确，模型生成内容/参数已错；匹配条件复现 | 只看到最终答案错 |
| Skill | 确认加载的规则本身有错，单变量替换/关闭后改善，重复配对支持 | 仅看到界面存在某 Skill |
| Harness | 正确附件/调用已提交，但传递、执行、持久化或交付出现可定位偏差；重放/独立文件检查支持 | 模型没调用工具，或不同模型得分不同 |
| 外部依赖 | 工具服务原始错误及独立故障证据 | 一句“网络问题” |
| 评测者 | 漏附件、控制工具误点、评分脚本错误等可复核记录 | 为失败事后找借口 |
| 混合/未知 | 输入不可见、多个因素同时变化或证据缺口 | 不应强行选一个责任方 |

现象置信度：高=原件/日志可直接验证；中=仅局部可见记录；低=转述。原因置信度：高=直接定位+匹配复现/单变量干预+排查主要替代解释；中=直接定位但仍有混杂；低=相关性猜测。不得随意写“90%确定”。
每个结论写：主张、适用任务/配置、证据路径与行号/时间戳、反例或替代解释、置信等级及理由。人工截图只能证明可见状态，不能证明隐藏工具调用或模型真实输入。

## 9. 证据与复核
每次目录：runs/<protocol>/<task>/<product>/<repeat>/。
保存 config.json、prompt-round*.txt、events.jsonl、对话导出/脱敏截图、inputs-manifest.json、round*/原始产物、checks.json、manual-review.csv、attribution.md、evidence-manifest.json。
events 至少含：时间、用户发送、附件完成、可见工具请求/返回、权限确认、错误、完成声明、下载、第二轮发送。无法导出的事件明确标“观察笔记”，不冒充原生日志。不索要隐藏思维链。

公开材料不包含登录令牌、个人侧栏历史、企业知识库内容；保存脱敏说明和原件哈希，结果数值不改。无法公开的证据不能支持“任何人都能复核”的强结论。
第二评审者可独立复评；个人作业无他人参与时，隔至少24小时将产物匿名打乱自行复评，明确不是独立双评。保存初评、复评、分歧和裁决。关键分歧先改规则，再对五款统一重评；改规则不得只利好某款。

## 10. 最终交付与推进门槛
公开仓库需包含：本方案、任务卡/输入/参考结果、验收器和测试、产品配置表、全部有效与无效运行索引、证据、评分明细、归因案例、报告、ChangeLog与周报。
报告正文固定为：研究问题→方法与环境→任务覆盖→五款逐任务结果→执行差异→失败案例与归因→置信依据→限制→复核方法。主表每个数字必须能找到检查项和 run_id。

阶段门槛：
1. 方案：四任务卡齐全、输入可生成、评分无歧义；本次交付到这里。
2. 试跑：每个任务至少五款各一次，新任务检查参考答案/验收器；旧 T02 试跑仅作校准材料。
3. 冻结：配置、预算、顺序、规则和证据采集都可执行；提交一个不可变 Git SHA。
4. 正式：完成60个有效试验（另列无效/受阻），不得用试跑替代。
5. 报告：复评通过、每条结论有证据；缺失则明确阶段报告，不伪称完整竞品排名。

每周六整理本周进展、难点突破、下周计划以及仓库/ChangeLog/周报链接。此方案不自动发送邮件。
最大执行预算为90轮×20分钟=30小时模型运行上限，另需预检、下载、复评与归因；实际用时记录后再估计。若时间不足，发布阶段报告，或在正式前统一缩减设计并改版本，不在看完结果后删任务。
