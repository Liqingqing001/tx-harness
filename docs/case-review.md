# 案例池与归因复核

每个Case记录 case_id、run_id、产品/任务/协议版本、最早可确认偏差、预期与实际、证据文件及时间戳/行号、候选原因、替代解释、对照实验、结论、现象置信度、原因置信度、评审人和日期。

## 分类与证据要求
- model：确认模型接收到正确输入、工具定义和返回，输出已出错；最好在匹配环境中复现。没有输入可见性不得仅凭结果归责。
- skill：确认Skill实际加载，定位其定义问题，并通过只替换/关闭该Skill的配对实验支持。
- harness：确认在上传、上下文传递、工具路由、状态/文件持久化等执行环节出现偏差；区分模型发出的错误参数与平台传错参数。可用预制正确调用或相同输入的重放检查。
- external：工具服务/网络的独立故障证据；不要自动把所有工具错误归到外部。
- evaluator：验收器bug、政策歧义、过时答案或采集错误；修正规则后统一重评所有产品。
- mixed/unknown：因果无法分离或缺少所需记录。

置信度：现象高=原始产物/日志明确证实；中=可见记录不完整；低=主观转述。原因高=直接证据+匹配条件复现/单变量干预+检查主要替代解释；中=直接定位但残余混杂；低=仅相关性。置信度不是随意填写的概率。

## 分流与闭环
真实失败→Case池→复核规则→定位原因→形成最小复现→纳入版本化错题集→后续版本回归。真实成功可成为黄金样本，但必须核验并记录适用范围。未执行的挑战用例只列计划。
无法修改商业产品时，交付可复现问题报告与证据，不声称已修复。对原方案的修正必须与对产品的修正分开记录。

## 过程证据边界
只采集合法可见/可导出的信息，不要求隐藏推理。截图按实际步骤命名；保存原始产物及SHA256；脱敏副本记录处理内容，不能修改结果数值。无公开证据的判断标为不可公开复核，不进入公开强结论。
